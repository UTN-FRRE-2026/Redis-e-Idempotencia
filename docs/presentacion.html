El problema

Las aplicaciones no corren en un solo servidor: corren varias copias del mismo servicio (réplicas) para aguantar carga y no caerse si una falla.

1 · Lentitud

Si cada pedido va a la base de datos, todo se vuelve lento.

2 · Pedidos repetidos

Si un cliente reintenta un pago, puede terminar pagando dos veces.

Redis resuelve ambos: es una memoria rápida y compartida por todas las réplicas.

cliente → nginx (:8080) → api-1 / api-2 → Redis + Postgres

Los componentes

ServicioRol
nginxBalanceador round-robin; único puerto expuesto (8080)
api-1, api-2Dos réplicas de la misma API (Node + TypeScript)
redisCaché + claves de idempotencia (AOF activado)
postgresFuente de verdad (productos y pagos)

Cada réplica tiene su propia memoria y no comparten nada → por eso el estado va en Redis.

¿Qué es Redis?

  • Base de datos que guarda todo en memoria RAM → responde en < 1 ms.
  • Funciona como un diccionario clave–valor: producto:1 → {...}.
  • TTL: a cada clave le podés poner tiempo de vida; Redis la borra sola.
  • Operaciones atómicas: se ejecutan de a una, sin que otra se meta en el medio.
  • AOF: anota cada escritura en disco y la recupera al reiniciar.
TEMA 1

Caché con Redis

Guardar una copia de un dato que se pide mucho, para no ir a la base cada vez.

HIT — el dato estaba en caché → respuesta instantánea (~5 ms)
MISS — no estaba → se busca en la base (~500 ms) y se guarda copia

Patrón cache-aside

  1. La API busca en Redis → GET producto:1
  2. Si no está: consulta Postgres y guarda copia con TTL → SET producto:1 ... EX 20
  3. Al modificar (PUT): actualiza Postgres y borra la copia → DEL producto:1

Se llama "caché al costado" porque la aplicación decide cuándo leer/escribir la caché; la base no sabe que existe.

TEMA 2

Idempotencia y deduplicación

Una operación es idempotente si hacerla una o muchas veces deja el mismo resultado.

Leer un producto ✅ — apretar el botón del ascensor ✅
Cobrar NO ❌ — cada cobro repetido le saca plata al cliente

Llegan repetidos por timeouts, doble clic, reintentos automáticos o colas "al menos una vez".

La Idempotency-Key

El cliente genera un identificador único (UUID) por cada pago y lo manda en el header. Todos los reintentos llevan la misma clave.

El servidor la anota y, si la vuelve a ver, no cobra de nuevo: devuelve la misma respuesta de la primera vez.

Es el mismo mecanismo que usan pasarelas de pago reales, como Stripe. La deduplicación es la misma idea aplicada a mensajes con ID.

Cómo funciona en la API


POST /pagos  con  Idempotency-Key: abc

SET idem:abc {"estado":"procesando"} NX EX 86400
#          NX = "guardar solo si No eXiste"  (atómico)
#          → si llegan 20 pedidos a la vez, SOLO UNO gana
  • Si ganó: cobra, guarda en Postgres, marca la clave completado + respuesta.
  • procesando → 409 "reintentá en unos segundos"
  • completado → devuelve la respuesta guardada + header Idempotent-Replayed
  • Misma clave con otros datos → 422 (error del cliente)

¿Y si Redis se cae? 04_redis_caido

Caché → fail-open

Sin Redis las consultas van directo a Postgres. Más lento, pero funciona.

Pagos → fail-closed

Se rechazan con 503 antes que arriesgar un cobro doble.

Un pago hecho antes de la caída no se re-cobra: la clave sobrevivió al reinicio gracias al AOF (Redis la había guardado en disco).

Idea común: el estado local por proceso no alcanza. Lo vimos 3 veces: balanceo de nginx, caché e idempotencia.

Conclusión

Redis resuelve ambos temas porque es una memoria compartida, rápida y con operaciones atómicas (SET NX).

Pero no es gratis: es otra pieza que se puede caer, vive en RAM y sus copias pueden quedar desactualizadas.

Por eso cada uso decide qué pasa cuando falla: la caché sigue (solo cuesta velocidad); los pagos se frenan (un error cuesta plata).

La idempotencia no evita que lleguen pedidos repetidos:
evita que tengan efecto.
